# 第一章：AI Agent 与项目基础（1-20）

## 1. 场景：你刚接手 `babyGrowAi` 项目

**问题**：请结合本项目，说明 AI Agent 和普通 LLM 调用有什么区别？

**参考答案**：

普通 LLM 调用是“输入 prompt → 输出 JSON”，例如 `OllamaGateway.chat_sync(messages, format=schema)`。AI Agent 则是能感知环境、自主决策、循环迭代的系统。未来改造后的 `RecipeRAGService` 可以感知家长输入和宝宝画像、规划调用知识库/天气/生长曲线、记忆过敏史、执行推荐并记录日志。当前项目还处于固定 pipeline 阶段，但已具备 Agent 雏形。

---

## 2. 场景：家长输入“今天宝宝 8 个月，便秘，不想吃青菜”

**问题**：如果把这条链路改造成 Agent，需要哪些核心模块？

**参考答案**：

需要 `QueryPlannerAgent`（解析意图与约束）、`RetrieverAgent`（检索知识库）、`SafetyAgent`（检查过敏原与禁忌）、`RecipeAgent`（生成推荐）、`CriticAgent`（自检输出）、`Memory`（查询 `baby_meal_history` 避免重复）、`Logger`（写入 `ai_decision_logs`）。

---

## 3. 场景：家长在对话中追问“那明天呢？”

**问题**：这属于 Agent 的哪种能力？当前项目是否支持？

**参考答案**：

这是短期记忆（对话上下文）。当前项目 API 是无状态的，每次请求只处理当前请求。要支持多轮对话，需要前端维护 `conversation_id`，后端增加 `ConversationHistory` 表或 Redis 缓存。

---

## 4. 场景：`OllamaGateway` 只做了调用和重试

**问题**：它算不算一个 Agent？为什么？

**参考答案**：

不算。`OllamaGateway` 是工具/能力层，只负责 HTTP 调用 Ollama、失败重试、流式封装，没有自主规划、记忆、多步决策。它是构建 Agent 的基础设施。

---

## 5. 场景：你要向实习生介绍 `babyGrowAi` 的 AI 部分

**问题**：用一句话概括本项目的 AI 链路。

**参考答案**：

家长输入需求 → 从 PostgreSQL 检索辅食知识并过滤规则 → 把结果和 prompt 发给 Ollama 本地模型 → 模型输出结构化推荐 JSON → 前端展示菜品、原因和忌口。

---

## 6. 场景：`recipe_rag.py` 中的 `recommend()` 方法

**问题**：Chain 和 Agent 有什么区别？本项目现在用哪个？

**参考答案**：

Chain 是固定流程，`recipe_rag.py` 中 `recommend()` 就是 Chain：规则过滤 → 检索 → 拼装 prompt → LLM 生成 → 解析 JSON。Agent 是动态流程，LLM 自己决定调用哪些工具。当前推荐步骤确定，用 Chain 更合适。

---

## 7. 场景：`BabyRecordExtractor` 提取失败时换一种 prompt 再试

**问题**：这属于 ReAct 吗？

**参考答案**：

是简化版 ReAct：Thought（提取失败）→ Action（换 prompt / 降低 temperature 再调用）→ Observation（第二次输出）→ Thought（判断是否合法）。

---

## 8. 场景：家长输入“拉不出”，系统推荐膳食纤维辅食

**问题**：这个过程中，Agent 的“观察”是什么？

**参考答案**：

观察是执行动作后获得的环境反馈。这里指对 query 做 embedding 后检索到的 chunk，例如“南瓜红薯泥富含膳食纤维”。如果检索为空，观察告诉 Agent 需要降级或改写 query。

---

## 9. 场景：`RecipeRAGService` 拿到检索结果后直接生成推荐

**问题**：如果中间加入“模型自检”步骤，有什么好处？

**参考答案**：

可以检查推荐菜品是否重复、是否有过敏原遗漏、推荐理由是否与 chunk 一致、低置信度时返回“建议咨询医生”。这会增加延迟，但能提升安全性。

---

## 10. 场景：推荐结果不稳定，同样输入有时输出不同

**问题**：这体现了 AI 项目与传统软件工程的什么差异？

**参考答案**：

传统软件是确定性的，`f(x)=y` 永远相同。AI 系统是概率性的，受 temperature、top_p、模型采样、检索结果影响。因此 AI 项目需要评估、监控、版本管理和 A/B 测试。

---

## 11. 场景：家长问“宝宝能吃蜂蜜吗？”，模型答“可以吃一点”

**问题**：这是什么问题？在本项目中如何防范？

**参考答案**：

这是幻觉 + 安全风险。1 岁前宝宝不能吃蜂蜜。本项目应通过 `RuleEngine` 强制把蜂蜜加入 `avoid_items`，prompt 明确“1 岁前禁止蜂蜜”，输出前用规则二次校验。

---

## 12. 场景：你给团队做 RAG 入门培训

**问题**：请用“食谱推荐”解释 RAG。

**参考答案**：

RAG = 检索 + 生成。家长输入“便秘吃什么”，用 embedding 从 `knowledge_chunks` 中找到相关食谱，把检索到的 chunk 和 prompt 一起给 LLM，模型基于检索内容生成推荐 JSON。这样模型基于项目知识库回答，减少幻觉。

---

## 13. 场景：业务方问“为什么不直接微调模型，而要搞 RAG？”

**问题**：请结合本项目说明 RAG 和 Fine-tuning 的选择。

**参考答案**：

RAG 知识更新快、成本低、可解释性强（有 source_refs）、幻觉少；Fine-tuning 适合改变模型能力或风格，但成本高、更新慢。本项目知识库频繁更新新食谱和指南，用 RAG 更灵活。

---

## 14. 场景：产品想支持“智能问答 + 推荐 + 记录”一体

**问题**：引入 Agent 是否过度设计？

**参考答案**：

如果推荐步骤固定，引入 Agent 是过度设计。但如果需要根据家长意图动态选择功能、调用多个工具、多轮对话，Agent 是合理选择。关键是任务是否需要动态规划。

---

## 15. 场景：你发现 prompt 散落在 `prompts/recipe.py`、`prompts/extraction.py` 等文件中

**问题**：这属于什么反模式？

**参考答案**：

“Prompt 硬编码、无版本管理”的反模式。改进：把 prompt 集中到 `prompts/` 目录，用版本号管理，变更走 CR，支持 A/B 测试。

---

## 16. 场景：`recipe_rag.py` 拼装 prompt 时检索到的 chunk 很长

**问题**：这会带来什么问题？

**参考答案**：

可能超过模型上下文窗口，导致信息截断、关键信息丢失、成本增加。需要控制 chunk 数量和长度，或做 chunk 压缩/摘要。

---

## 17. 场景：产品要求每周统计推荐准确率

**问题**：为什么 AI 项目特别需要监控？

**参考答案**：

LLM 输出是概率性的，即使代码没改，模型版本、prompt、知识库变化都可能影响效果。需要监控推荐采纳率、用户反馈、幻觉率、响应时间、错误率。

---

## 18. 场景：团队要建立 LLMOps 流程

**问题**：对于本项目，LLMOps 至少包含哪些内容？

**参考答案**：

Prompt 版本管理、模型版本管理（Ollama tag）、知识库版本管理（ingest hash）、离线评测、在线监控、反馈闭环（家长反馈 → 更新知识库/prompt）。

---

## 19. 场景：你在 `prompts/recipe.py` 中增加更多 few-shot 示例

**问题**：但示例太多会占用上下文窗口，怎么办？

**参考答案**：

精选高质量示例，每个场景 1-2 个；根据 query 动态选择最相关的 few-shot；使用 prompt 压缩/摘要技术；必要时用更短的中文表达。

---

## 20. 场景：实习生问“这个项目的 AI 部分最难的是什么？”

**问题**：你会怎么回答？

**参考答案**：

最难的不是调用 LLM，而是让宝宝饮食推荐安全（过敏原、月龄禁忌）、有依据（RAG + source_refs）、稳定输出合法 JSON、建立评估和反馈闭环。需要工程 + 业务 + 安全的综合考虑。

# 第二章：RAG 与知识库实战（21-40）

## 21. 场景：你打开 `babyGrowAi/data/guides/nutrition_guide.md`

**问题**：这些文档如何变成 `knowledge_chunks` 里的向量？

**参考答案**：

`app/knowledge/ingest.py` 读取 Markdown → 解析章节 → 切分成 chunk → `services/embedding.py` 调用 bge-m3 生成 embedding → 存入 `knowledge_chunks` 表。

---

## 22. 场景：对比 bge-m3 和 qwen2.5:7b 的 embedding 效果

**问题**：为什么 `services/embedding.py` 用 bge-m3？

**参考答案**：

bge-m3 是专门 Embedding 模型，体积小、速度快、对句子级语义对齐好、支持中英双语；qwen2.5:7b 是生成模型，用它做 embedding 成本高、延迟大。

---

## 23. 场景：`docker-compose.yml` 中 PostgreSQL 用了 `pgvector/pgvector:pg16`

**问题**：为什么不用普通 PostgreSQL？

**参考答案**：

普通 PostgreSQL 不支持向量类型和相似度查询。pgvector 提供 `vector` 类型、`cosine_distance` 函数、HNSW 索引加速 ANN 搜索。

---

## 24. 场景：`services/retrieval.py` 用 cosine distance 排序

**问题**：余弦距离和余弦相似度是什么关系？

**参考答案**：

余弦相似度 `cos(A,B)` 越接近 1 越相似；余弦距离 `1 - cos(A,B)` 越接近 0 越相似。pgvector 中 `<=>` 就是 cosine distance。

---

## 25. 场景：知识库里有 1000 个 chunk，查询时不能全表扫描

**问题**：应该建什么索引？

**参考答案**：

建 HNSW 索引：
```sql
CREATE INDEX idx_knowledge_chunks_embedding
ON knowledge_chunks USING hnsw (embedding vector_cosine_ops);
```

---

## 26. 场景：家长输入“娃便秘”，检索只召回了一条无关结果

**问题**：这是 recall 低还是 precision 低？

**参考答案**：

是 recall 低，相关知识没被召回。原因可能是 query 和 chunk 语义距离远、切分丢失关键词、相似度阈值太高。改进：query 改写、混合检索、降低阈值。

---

## 27. 场景：家长输入“红薯”，向量检索只召回“马铃薯泥”

**问题**：这种情况适合用什么检索策略？

**参考答案**：

Dense Embedding 语义泛化过头、关键词匹配缺失。应该用 Hybrid Search：Dense 召回语义相关，BM25 确保“红薯”关键词命中，再用 RRF 融合。

---

## 28. 场景：Dense 检索返回 10 条，BM25 也返回 10 条，如何合并？

**问题**：RRF 公式是什么？

**参考答案**：

`score = Σ 1 / (k + rank_i)`，通常 k=60。不需要归一化分数，只用排名。

---

## 29. 场景：家长输入“这两天拉不出”

**问题**：检索前需要对 query 做什么处理？

**参考答案**：

Query 改写：口语化“拉不出” → 标准表达“便秘” → 扩展相关食材“膳食纤维、南瓜、红薯、菠菜、梨、燕麦” → 明确为“8个月宝宝便秘辅食推荐”。

---

## 30. 场景：向量召回 20 条 chunk，但前几条相关性不高

**问题**：可以在哪个阶段优化？

**参考答案**：

加 Re-ranking。用 cross-encoder 同时看 query 和 chunk，比双塔 Embedding 更精确，只对 Top-20 重排，计算量可控。

---

## 31. 场景：`data/recipes/` 里的一篇食谱有“食材、做法、营养、月龄”四章节

**问题**：直接按章节切 chunk 有什么风险？

**参考答案**：

上下文断裂：“食材”chunk 丢失“适合 8 个月”和“质地软烂”；“做法”chunk 不知道过敏原提示，导致无法判断 chunk 是否适合当前宝宝。

---

## 32. 场景：为了解决上下文断裂，你想在每个 chunk 里保留文档元信息

**问题**：有哪些方法？

**参考答案**：

1. Metadata 注入：把 `age_min`、`texture_level`、`allergens` 写入 `chunk_metadata`
2. Parent Document Retrieval：检索 chunk，返回完整 parent document
3. 重叠切分：相邻 chunk 共享文字
4. HyDE：用 LLM 生成理想答案文档再检索

---

## 33. 场景：检索到 chunk 后发现它缺少完整食谱信息

**问题**：什么是 Parent Document Retrieval？怎么实现？

**参考答案**：

检索用细粒度 chunk，但把完整 parent document 作为 LLM 上下文。实现：`knowledge_chunks` 表增加 `document_id`，检索到 chunk 后 join `knowledge_documents`，把完整 content 传给 LLM。

---

## 34. 场景：家长输入“宝宝便秘辅食推荐”

**问题**：HyDE 在这个场景下怎么工作？

**参考答案**：

1. LLM 根据 query 生成理想答案：“8个月宝宝便秘可食用富含膳食纤维的辅食，如南瓜红薯泥、燕麦香蕉泥...”
2. 对理想答案做 embedding
3. 用这个向量检索最相似 chunk

优点是把“问题”转成“答案形式”更容易匹配；缺点是多一次 LLM 调用。

---

## 35. 场景：你需要把一批新食谱加入知识库

**问题**：`app/knowledge/ingest.py` 的主要步骤是什么？

**参考答案**：

遍历 `data/recipes/*.md` → 解析标题/月龄/食材/做法/营养 → 插入 `knowledge_documents`、`recipes`、`recipe_ingredients` → 生成 chunk → `EmbeddingService.embed()` 生成向量 → 插入 `knowledge_chunks`。

---

## 36. 场景：营养指南更新了，需要只更新变化的部分

**问题**：怎么做增量更新？

**参考答案**：

给每个文档计算 hash，入库时记录 `doc_hash`。再次 ingest 时，先查 hash 是否变化，只有变化的文档才重新切分和 embedding，删除旧 chunk，插入新 chunk。

---

## 37. 场景：`RetrievalService.retrieve()` 需要过滤 8 个月宝宝且不含鸡蛋的食谱

**问题**：这种过滤怎么做？

**参考答案**：

把月龄和过敏原作为 metadata，SQL 过滤 + 向量检索结合。用 `knowledge_chunks` 关联 `recipes` 和 `recipe_ingredients`，过滤后按向量距离排序。

---

## 38. 场景：家长问“6个月宝宝可以吃芒果吗？”，系统推荐了芒果

**问题**：这是哪种 RAG 失败模式？

**参考答案**：

可能是检索失败（没召回到高敏水果提示）、过滤失败（规则没覆盖芒果）、生成不看上下文。应检查规则引擎、检索结果、prompt 约束。

---

## 39. 场景：家长输入“今天不知道吃什么”

**问题**：检索结果为空，怎么办？

**参考答案**：

Query 改写为“8个月宝宝辅食推荐”、使用通用推荐模板、返回原则性建议、提示家长补充具体需求、记录 query 用于优化知识库。

---

## 40. 场景：家长先问“8个月便秘”，再问“那明天呢？”

**问题**：多轮对话的 RAG 需要注意什么？

**参考答案**：

维护 `conversation_id` 和历史消息；对“明天呢”做指代消解，补全为“8个月宝宝便秘明天吃什么”；查询当日饮食记录避免重复；把历史和检索结果一起传给 LLM。

# 第三章：Prompt 工程与结构化输出（41-55）

## 41. 场景：你打开 `prompts/recipe.py` 发现 `SYSTEM_PROMPT` 很长

**问题**：System Prompt 的作用是什么？

**参考答案**：

设定模型角色和全局规则。本项目中角色是“专业婴幼儿营养师”，规则包括安全优先、月龄匹配、营养均衡、只基于知识库、不确定返回 INSUFFICIENT_EVIDENCE。System Prompt 影响模型整个对话行为和输出风格。

---

## 42. 场景：你在 prompt 里给了 3 个推荐示例

**问题**：这是 Zero-shot、One-shot 还是 Few-shot？

**参考答案**：

Few-shot（多个示例）。示例让模型学习输出格式、推荐风格和安全边界，但要精选避免过度拟合。

---

## 43. 场景：模型推荐的推荐理由总是“营养丰富”

**问题**：可以用 CoT 改进吗？

**参考答案**：

可以。在 prompt 中要求模型先分析月龄、食材、过敏原，再选择菜品并说明理由。这样推荐理由更具体、更可解释。

---

## 44. 场景：`build_recipe_prompt()` 把月龄、过敏原、质地拼成 user prompt

**问题**：为什么这些用户画像信息不放在 system prompt？

**参考答案**：

System prompt 是全局角色和规则，用户画像是本次请求的具体信息。放在 user prompt 避免 system prompt 过长，并让模型明确区分全局规则与本次输入。

---

## 45. 场景：`OllamaGateway.chat_sync()` 设置了 temperature

**问题**：推荐任务 temperature 应该高还是低？

**参考答案**：

应该低（0.1-0.3）。辅食推荐需要稳定、可预测、严格遵循 schema、减少幻觉。创意写作才需要高 temperature。

---

## 46. 场景：你设置 top_p=0.9

**问题**：这是什么意思？

**参考答案**：

只从累积概率达到 90% 的最小 token 集合中采样，限制候选范围，减少荒谬内容，同时保留一定多样性。

---

## 47. 场景：`recipe_rag.py` 中定义 JSON schema 传给 Ollama

**问题**：这个 schema 有什么用？

**参考答案**：

定义输出结构：字段名、类型、必填字段、数组长度限制、是否允许额外字段。Ollama 可转成 grammar 强制模型按 schema 输出。

---

## 48. 场景：模型有时输出 `instructions` 字段，但 schema 没要求

**问题**：这说明用的是 JSON Mode 还是 JSON Schema Mode？

**参考答案**：

说明可能用的是 JSON Mode 或 schema 约束不够严格。JSON Mode 只保证合法 JSON，不限制字段。应使用 JSON Schema Mode 并设置 `additionalProperties: false`。

---

## 49. 场景：`recipe_rag.py` 中 `json.loads(content)` 抛异常

**问题**：应该做哪些兜底处理？

**参考答案**：

捕获 JSONDecodeError；用正则提取 JSON 块；用 LLM 二次修复；记录错误日志和原始输出；返回 RecipeRecommendResponse(status="error", ...)。

## 50. 场景：家长输入“我家宝宝不爱吃青菜”，模型却推荐了青菜

**问题**：prompt 怎么避免这种情况？

**参考答案**：

在 prompt 中明确把“不喜欢的食物”作为强约束：必须避开宝宝不喜欢的食物：{disliked_foods}。同时后处理校验推荐结果中是否包含不喜欢的食材。

---

## 51. 场景：你发现 `SYSTEM_PROMPT` 越来越长，影响性能

**问题**：怎么优化？

**参考答案**：

精简重复描述；把 few-shot 示例放入 user prompt 并按需动态选择；删除不必要的修饰词；使用 prompt 压缩工具；必要时把长 prompt 拆成多层。

---

## 52. 场景：你要测试两个 prompt 版本的效果

**问题**：怎么做 A/B 测试？

**参考答案**：

按用户 ID 哈希分桶；A 组用 prompt v1，B 组用 prompt v2；收集推荐采纳率、好评率、响应时间；用统计方法判断差异是否显著；记录版本号便于回滚。

---

## 53. 场景：`prompts/extraction.py` 的 few-shot 示例只有 2 个

**问题**：示例数量是否越多越好？

**参考答案**：

不是。示例过多会占用上下文窗口，且可能让模型过度拟合示例格式。应覆盖主要场景，每个场景 1-2 个高质量示例，保持多样性。

---

## 54. 场景：模型有时输出“根据知识库内容”这类解释性文字

**问题**：prompt 如何约束？

**参考答案**：

在 system prompt 中明确要求“只输出 JSON，不要解释”或“不要输出与结果无关的说明性文字”。同时在后处理中校验输出是否符合 schema。

---

## 55. 场景：家长用方言输入“娃儿这两天屙不出”

**问题**：prompt 需要做哪些处理？

**参考答案**：

prompt 本身难以处理方言。需要增加预处理层：先做方言识别和标准化，转成标准普通话 query，再放入 prompt。可训练或 prompt 引导 LLM 做“方言 → 标准语”转换。

# 第四章：LLM 原理与选型（56-70）

## 56. 场景：团队讨论换模型

**问题**：什么是 LLM？本项目为什么选本地 Ollama 而不是 GPT-4？

**参考答案**：

LLM 是基于 Transformer 的大规模语言模型，能理解和生成自然语言。本项目选本地 Ollama 是因为：宝宝数据隐私敏感、本地部署成本低、网络延迟小、可控性高。GPT-4 能力更强但成本高、数据出域风险大。

---

## 57. 场景：你向同事解释模型为什么能看懂中文

**问题**：Transformer 的 Self-Attention 做了什么？

**参考答案**：

Self-Attention 让模型在处理一个词时同时关注句子中其他词，计算它们之间的相关性权重。例如“bank”在“river bank”和“bank account”中含义不同，Self-Attention 通过上下文判断。

---

## 58. 场景：qwen2.5:7b 模型文件很大

**问题**：什么是量化？本项目 Dockerfile 中 `q5_K_M` 是什么意思？

**参考答案**：

量化是把模型参数从高精度（FP32）转为低精度（INT8/INT4/5-bit），减少内存占用、加快推理。`q5_K_M` 表示 5-bit K-quant 中等混合量化，是 llama.cpp 的量化格式。

---

## 59. 场景：你希望模型更“听话”

**问题**：预训练和微调有什么区别？本项目是否微调了？

**参考答案**：

预训练是在大规模无标注语料上学习通用语言知识；微调是在特定任务数据上进一步训练。本项目直接使用 qwen2.5:7b 预训练模型，没有微调。未来可用 LoRA 在本地食谱数据上微调，提升领域理解。

---

## 60. 场景：你想用较低成本提升模型在辅食领域的表现

**问题**：LoRA 是什么？适合本项目吗？

**参考答案**：

LoRA（Low-Rank Adaptation）只训练少量低秩矩阵，大幅减少微调参数。适合本项目：数据量不大、需要快速迭代、本地 GPU 资源有限。可收集营养师标注数据做 LoRA 微调。

---

## 61. 场景：简单推荐用 7B 模型，复杂医学问题想用更强的

**问题**：什么是模型路由？

**参考答案**：

模型路由是根据请求特征选择合适模型的机制。例如简单推荐用本地 7B，复杂医学问题用云端大模型。实现方式：规则路由、分类器路由、强化学习路由。

---

## 62. 场景：模型偶尔会生成训练数据中的内容

**问题**：这是数据泄露吗？如何防范？

**参考答案**：

如果生成的是敏感训练数据片段，属于数据泄露风险。防范：使用本地模型、避免在训练集中包含敏感信息、输出过滤、限制模型输出与知识库的匹配检查。

---

## 63. 场景：你观察到模型推理时显存占用很高

**问题**：什么是 KV Cache？能优化吗？

**参考答案**：

KV Cache 缓存 Transformer 推理中的 Key 和 Value，避免重复计算，加速生成。优化：减少上下文长度、使用量化模型、合理设置 batch size。

---

## 64. 场景：模型输出总是“营养丰富”，缺乏个性

**问题**：是模型能力问题还是 prompt 问题？

**参考答案**：

更可能是 prompt 问题。模型倾向于给出安全、通用的回答。需要更具体的 CoT 指令和 few-shot 示例，要求模型结合食材具体说明理由。

---

## 65. 场景：模型有时答非所问

**问题**：可能是 temperature 太高吗？

**参考答案**：

可能。高 temperature 增加随机性，可能导致模型偏离主题。建议推荐任务使用低 temperature（0.1-0.3），并加强 prompt 约束。

---

## 66. 场景：家长连续提问，模型上下文越来越长

**问题**：如何处理上下文窗口限制？

**参考答案**：

- 截断早期不重要的对话
- 对历史对话做摘要
- 只保留最近 N 轮
- 使用支持更长上下文的模型
- 本项目 qwen2.5:7b 上下文 32K/128K，但建议控制 prompt 长度

---

## 67. 场景：你想让模型输出更确定的 JSON

**问题**：除了降低 temperature，还能做什么？

**参考答案**：

- 使用 JSON Schema Mode / Constrained Decoding
- 在 prompt 中明确要求“只输出 JSON”
- 后处理用 Pydantic 校验
- 失败后重试并降低 temperature

---

## 68. 场景：模型推荐中出现“燕窝”“海参”等高端食材

**问题**：这可能是什么问题？

**参考答案**：

可能是模型训练知识中的通用推荐，与本项目知识库不符，属于幻觉。应建立食材白名单，后处理校验 ingredients 是否在白名单中。

---

## 69. 场景：模型对“8个月”和“1岁”的推荐没有区别

**问题**：怎么让模型更重视月龄约束？

**参考答案**：

在 prompt 中突出月龄约束；用 RuleEngine 过滤不适合月龄的 chunk；在 schema 中无法直接约束，但可在 prompt 中反复强凋；后处理校验月龄。

---

## 70. 场景：你希望模型更理解家长情绪

**问题**：这需要什么能力？

**参考答案**：

需要情感理解和共情能力。可通过 prompt 引导模型识别家长焦虑情绪并给出温和回复；若长期优化，可用情感标注数据微调。

# 第九章：RAG 高级实战（101-120）

> 本章节是在第二章基础上的 20 道进阶题，聚焦 `baby-grow` 项目中 RAG 系统的深入优化与真实挑战。

## 101. 场景：家长输入“宝宝便秘但不爱吃青菜，能吃点什么？”

**问题**：这种多约束 query 如何设计检索策略？

**参考答案**：

需要 Query Decomposition：把原始 query 拆成“便秘 → 膳食纤维”和“不爱吃青菜 → 非青菜类高纤维食材”。分别检索后合并结果，再用 LLM 生成综合推荐。

---

## 102. 场景：你发现 bge-m3 对辅食领域术语召回不准

**问题**：怎么优化？

**参考答案**：

用领域数据对 Embedding 模型做继续训练或微调；收集辅食领域的同义词对（query-document）训练 bge-m3；或者在后处理做同义词映射。

---

## 103. 场景：一篇 3000 字的辅食指南无法直接切一个 chunk

**问题**：怎么做长文档 RAG？

**参考答案**：

先对文档做层次化摘要：文档级摘要 → 章节摘要 → chunk 摘要。检索时用摘要定位相关章节，再取原始 chunk 作为上下文。

---

## 104. 场景：Dense 检索召回“南瓜粥”，但家长问的是“红薯”

**问题**：如何增强同义词和近义词召回？

**参考答案**：

建立食材同义词表（南瓜↔倭瓜、红薯↔地瓜）；做 Query Expansion 把同义词加入检索；用 Hybrid Search 结合 BM25 命中关键词。

---

## 105. 场景：你只有 100 条标注数据

**问题**：能微调 Embedding 模型吗？

**参考答案**：

可以，但数据量偏少，适合用 LoRA 或 Sentence-BERT 的轻量微调。建议先做数据增强：用 LLM 生成 query-paraphrase 对，扩充训练集。

---

## 106. 场景：召回结果中有些 chunk 内容互相矛盾

**问题**：怎么处理？

**参考答案**：

矛盾可能是因为 chunk 来源不同（如不同月龄段的指南）。应让 chunk 携带来源和版本信息，检索时按宝宝月龄过滤；生成前让 LLM 做一致性判断，选择最相关、最有时效性的 chunk。

---

## 107. 场景：你想用 cross-encoder 做重排序

**问题**：部署时有什么注意事项？

**参考答案**：

Cross-encoder 比双塔慢，只对 Top-K（如 20-50）做重排；不能对全库使用；需要 GPU 或足够 CPU；注意延迟预算。

---

## 108. 场景：检索延迟达到 500ms

**问题**：怎么优化？

**参考答案**：

- 加 HNSW 索引
- 减少 Top-K
- 使用缓存
- 做查询预过滤
- 异步预取热门 query 结果

---

## 109. 场景：新上线一批食谱，需要立即生效

**问题**：如何做到增量且实时更新向量库？

**参考答案**：

- 用消息队列或定时任务触发 ingest
- 只处理新增/变更文档
- 更新 `knowledge_chunks` 表中对应 chunk
- 更新 HNSW 索引
- 提供版本号便于回滚

---

## 110. 场景：家长输入“今天吃什么”

**问题**：这种无明确意图的 query 怎么处理？

**参考答案**：

- 意图识别：判断是随意推荐还是有隐藏需求
- 结合宝宝画像（月龄、季节、历史）生成默认推荐
- 返回通用推荐模板
- 反问家长具体需求

---

## 111. 场景：知识库中有多个来源的指南

**问题**：不同来源指南冲突怎么办？

**参考答案**：

为每个 chunk 标注来源、版本、置信度。冲突时优先采纳权威来源（如中国营养学会），或提示 LLM 以最新指南为准；高风险场景返回“存在不同建议，请咨询医生”。

---

## 112. 场景：你想在检索时结合宝宝历史饮食

**问题**：如何实现个性化检索？

**参考答案**：

把宝宝画像向量化，与 query 向量融合（如加权拼接），或把历史饮食偏好拼入检索 query。也可以后处理过滤掉历史重复菜品。

---

## 113. 场景：召回的 chunk 很长，超过上下文预算

**问题**：怎么压缩？

**参考答案**：

- 用 LLM 对 chunk 做摘要
- 只保留与 query 相关的句子
- 分段压缩后再拼接

---

## 114. 场景：你想知道某个 query 的检索效果好不好

**问题**：用什么指标？

**参考答案**：

- Recall@K
- Context Precision@K
- NDCG
- 人工相关性判断

---

## 115. 场景：系统上线后检索准确率下降

**问题**：可能原因？

**参考答案**：

- 知识库更新后 chunk 质量变差
- Embedding 模型版本变化
- Query 分布偏移
- 索引损坏或没更新
- HNSW 参数不当

---

## 116. 场景：你想做跨语言检索（中文 query 搜英文食谱）

**问题**：怎么实现？

**参考答案**：

使用多语言 Embedding 模型（如 bge-m3 支持多语言）；或把 query 和文档翻译到同一语言；或用多语言向量空间对齐。

---

## 117. 场景：新用户没有历史饮食记录

**问题**：冷启动怎么做？

**参考答案**：

- 按月龄推荐通用入门食谱
- 询问家长偏好和过敏信息
- 使用热门推荐
- 逐步收集反馈优化

---

## 118. 场景：你想评估 RAG 改动是否值得上线

**问题**：ROI 怎么算？

**参考答案**：

对比改动前后：推荐采纳率、用户好评率、响应时间、运维成本、开发成本。综合计算用户价值提升与投入成本。

---

## 119. 场景：检索结果中出现“果汁”相关 chunk

**问题**：但 1 岁前不建议喝果汁，怎么处理？

**参考答案**：

在规则引擎中把果汁加入低月龄禁用清单；检索后做安全过滤；生成 prompt 中强调月龄禁忌；后处理校验推荐结果。

## 120. 场景：你要设计一个 RAG 系统的持续优化闭环

**问题**：具体怎么做？

**参考答案**：

1. 收集用户查询和反馈
2. 标注 bad case
3. 分析检索失败原因（query、chunk、模型）
4. 迭代 query 改写、chunk 策略、prompt
5. 跑离线评测
6. A/B 测试上线
7. 监控线上指标
8. 回到步骤 1
