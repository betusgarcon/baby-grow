# 第一章：AI Agent 入门基础（1-20）

## 1. 什么是 AI Agent？和传统的 LLM 应用有什么区别？

**考点**：Agent 定义、自主决策、工具调用。

**参考答案**：

AI Agent 是一种能感知环境、自主决策并执行动作的系统。与传统 LLM 应用相比，Agent 不只是“一问一答”，而是可以：
- 分解复杂任务
- 调用外部工具（搜索、数据库、API）
- 根据反馈循环迭代
- 在多步骤中保持状态

传统 LLM 应用类似函数：`f(user_input) -> response`；Agent 更像一个循环：`observe -> think -> act -> observe -> ...`。

---

## 2. Agent 的基本组成模块有哪些？

**考点**：Agent 架构。

**参考答案**：

典型 Agent 包括：
- **感知（Perception）**：接收用户输入、环境状态
- **规划（Planning）**：决定下一步做什么
- **记忆（Memory）**：短期记忆（对话上下文）和长期记忆（用户画像、历史记录）
- **工具（Tools）**：调用外部 API、数据库、搜索引擎等
- **执行（Action）**：执行工具调用或返回结果
- **反馈（Feedback）**：根据结果调整计划

---

## 3. 什么是 ReAct 模式？

**考点**：Reasoning + Acting。

**参考答案**：

ReAct = Reasoning + Acting。模型在每一步先进行推理（Thought），再决定行动（Action），然后观察结果（Observation），循环直到完成。

示例：
```
Thought: 用户问"北京今天天气"，我需要调用天气 API。
Action: call_weather_api(city="北京")
Observation: {"temperature": 25, "weather": "晴"}
Thought: 已有结果，可以回复。
Final Answer: 北京今天晴天，25度。
```

---

## 4. Agent 和 Chain 有什么区别？

**考点**：LangChain/LangGraph 概念。

**参考答案**：

- **Chain**：固定执行流程，如 `prompt -> LLM -> parser`，适合任务步骤确定的场景。
- **Agent**：动态决策流程，LLM 自己决定调用什么工具、调用几次，适合任务步骤不确定的场景。

Chain 更可控、延迟更稳定；Agent 更灵活，但更难调试。

---

## 5. 什么是工具调用（Tool Calling / Function Calling）？

**考点**：Tool Use 基础。

**参考答案**：

工具调用是指 LLM 输出一个结构化的函数调用请求（函数名 + 参数），由外部系统执行后，把结果返回给 LLM。

流程：
1. 用户提问
2. LLM 判断需要调用工具
3. 系统执行工具
4. 工具结果返回 LLM
5. LLM 生成最终回复

---

## 6. 当前项目里的 `OllamaGateway` 算不算 Agent？

**考点**：对项目组件的理解。

**参考答案**：

不算完整的 Agent。`OllamaGateway` 只是一个模型调用网关，负责：
- 调用 Ollama API
- 重试
- 流式处理

它没有自主规划、工具调用、记忆等 Agent 能力。但它是构建 Agent 的基础组件。

---

## 7. 什么是单 Agent、多 Agent、Agent 团队？

**考点**：Agent 组织形式。

**参考答案**：

- **单 Agent**：一个 LLM 完成所有任务。
- **多 Agent**：多个 Agent 协作，每个 Agent 负责不同子任务。
- **Agent 团队**：Agent 之间有明确分工和通信机制，如主管-工人模式、平等协作模式。

本项目未来可把 `RecipeRAGService` 拆成 `PlannerAgent`、`RetrieverAgent`、`SafetyAgent` 等。

---

## 8. Agent 的记忆分为哪几类？

**考点**：Memory 分类。

**参考答案**：

- **短期记忆**：当前对话上下文，随会话结束消失
- **长期记忆**：用户画像、历史偏好、知识库
- **外部记忆**：数据库、向量库、缓存（Redis）

在辅食推荐场景中，宝宝过敏原、喜欢/不喜欢的食物属于长期记忆。

---

## 9. Agent 中的规划（Planning）有哪些方式？

**考点**：Planning 策略。

**参考答案**：

- **单步规划**：一次生成完整计划，然后执行
- **多步规划**：ReAct，每步根据观察调整
- **分层规划**：高层做宏观计划，低层做具体执行
- **反思规划**：执行后反思并修正计划

本项目当前是固定 pipeline，未来可引入动态规划。

---

## 10. 什么是观察（Observation）？为什么重要？

**考点**：Agent 循环。

**参考答案**：

观察是 Agent 执行动作后获得的环境反馈。没有观察，Agent 无法知道自己的行为是否有效，也就无法修正计划。

在 RAG 推荐中，检索到的 chunk 就是观察；如果检索结果质量差，Agent 应调整 query 重新检索。

---

## 11. Agent 和传统软件工程最大的不同是什么？

**考点**：范式转变。

**参考答案**：

传统软件工程是确定性的：输入 -> 固定逻辑 -> 输出。

AI Agent 是概率性的：
- 相同输入可能产生不同输出
- 行为由模型能力决定，而非完全由代码决定
- 需要评估、监控、反馈闭环
- 需要考虑幻觉、偏见、安全等风险

---

## 12. 什么是 LLM 的幻觉（Hallucination）？

**考点**：幻觉基础。

**参考答案**：

幻觉是指 LLM 生成与事实不符、无中生有或与上下文矛盾的内容。

在辅食推荐中，幻觉可能表现为：
- 推荐知识库中没有的食材
- 编造不存在的营养成分
- 给出不适合宝宝月龄的建议

---

## 13. 如何减少 Agent 中的幻觉？

**考点**：幻觉治理。

**参考答案**：

- **RAG**：让模型基于检索到的真实知识生成
- **约束输出**：用 schema、grammar 限制输出
- **事实校验**：后处理检查生成的实体是否在白名单
- **置信度评分**：低置信度时拒绝或提示
- **人工审核**：高风险场景加入人工复核

---

## 14. 什么是检索增强生成（RAG）？

**考点**：RAG 定义。

**参考答案**：

RAG = Retrieval-Augmented Generation。它先把用户 query 用向量检索找到相关文档，再把文档作为上下文交给 LLM 生成答案。

RAG 结合了检索的准确性和生成的灵活性，能减少幻觉，适合需要基于特定知识库回答的场景。

---

## 15. RAG 和普通 Fine-tuning 有什么区别？

**考点**：RAG vs Fine-tuning。

**参考答案**：

| 维度 | RAG | Fine-tuning |
|------|-----|-------------|
| 知识更新 | 快，更新知识库即可 | 慢，需要重新训练 |
| 成本 | 低 | 高 |
| 灵活性 | 高 | 中 |
| 幻觉 | 较少 | 仍可能 |
| 适用 | 知识频繁变动 | 能力/风格固化 |

两者可结合：RAG 提供知识，微调提升模型遵循指令和领域理解能力。

---

## 16. Agent 开发中常见的反模式有哪些？

**考点**：工程经验。

**参考答案**：

- **过度 Agent 化**：本可用固定 pipeline 解决，却硬要 Agent 动态决策
- **忽视评估**：只上线不监控，不知道效果好不好
- **Prompt 硬编码**：没有版本管理，无法复现
- **不做兜底**：LLM 失败时系统直接崩溃
- **记忆无边界**：上下文无限增长，成本和质量都下降

---

## 17. 什么是上下文窗口（Context Window）？

**考点**：LLM 上下文。

**参考答案**：

上下文窗口是 LLM 能同时处理的输入 token 数量上限。超过上限的内容会被截断或无法处理。

本项目使用 qwen2.5:7b，典型上下文窗口为 32K 或 128K。设计 RAG 时，检索到的 chunk 总和不能超过上下文窗口。

---

## 18. 为什么 Agent 需要评估和监控？

**考点**：LLMOps 基础。

**参考答案**：

因为 LLM 输出是概率性的，不像传统软件那样容易通过单元测试保证正确性。需要：
- 离线评估：测试集、指标
- 在线监控：延迟、错误率、用户反馈
- 可追溯：日志、trace
- 可回滚：模型版本、prompt 版本

---

## 19. 什么是 LLMOps？

**考点**：LLMOps 概念。

**参考答案**：

LLMOps = Large Language Model Operations。它包括：
- 模型管理：版本、部署、切换
- Prompt 管理：版本、A/B 测试
- 数据管理：训练数据、评测数据、反馈数据
- 评估：离线指标、在线指标
- 监控：延迟、成本、幻觉、安全
- 反馈闭环：用户反馈驱动迭代

---

## 20. 如果你想让刚入门的同学快速理解本项目 AI 部分，你会怎么介绍？

**考点**：总结能力。

**参考答案**：

本项目 AI 部分可概括为“一个 RAG 推荐 + 一个文本提取”：
- 家长输入文本或选择需求
- 系统从 PostgreSQL 中检索相关辅食知识
- 同时用规则引擎过滤过敏原、月龄禁忌
- 把检索结果和规则结果一起传给 Ollama 本地大模型
- 模型输出结构化的推荐 JSON
- 前端展示推荐菜品、原因、忌口

文本提取则是把家长输入的非结构化喂养记录，转成结构化的数据存入数据库。

# 第二章：RAG 与知识库（21-40）

## 21. 什么是 Embedding？为什么 RAG 需要它？

**考点**：Embedding 基础。

**参考答案**：

Embedding 是把文本、图片等数据映射成固定维度向量的技术。语义相似的文本在向量空间中距离近。

RAG 需要 Embedding 是因为：用户 query 和文档中的词语可能不完全相同但语义相近（如“便秘”和“拉不出”），通过向量检索可以找到语义相关的文档。

---

## 22. 常见的 Embedding 模型有哪些？本项目为什么选 bge-m3？

**考点**：Embedding 选型。

**参考答案**：

常见模型：OpenAI text-embedding-3、BGE、M3E、Sentence-BERT、E5。

选 bge-m3 的原因：
- 开源免费
- 中英双语效果好
- 模型体积小，本地部署压力小
- 支持 Dense 和 Sparse 混合检索

---

## 23. 什么是向量数据库？本项目用了哪个？

**考点**：向量数据库。

**参考答案**：

向量数据库是专门存储和检索向量的数据库，支持相似度搜索（如余弦相似度、点积）。

本项目使用 PostgreSQL + pgvector 扩展。pgvector 允许在 PostgreSQL 中直接存储 `vector` 类型，并提供 `cosine_distance`、`l2_distance` 等函数。

---

## 24. 什么是余弦相似度？

**考点**：相似度度量。

**参考答案**：

余弦相似度衡量两个向量方向的接近程度，计算它们夹角的余弦值。

公式：`cos(θ) = (A·B) / (||A|| * ||B||)`

值域 [-1, 1]，越接近 1 表示越相似。本项目用 `cosine_distance = 1 - cosine_similarity` 做排序。

---

## 25. 什么是 ANN（近似最近邻）？

**考点**：向量检索。

**参考答案**：

ANN 是在大规模向量集中快速找到与查询向量最相似的 K 个向量的算法。它牺牲极小精度换取大幅速度提升。

常见索引：HNSW、IVF、PQ。pgvector 支持 HNSW 索引。

---

## 26. 什么是召回率和精确率？

**考点**：检索评估。

**参考答案**：

- **召回率 Recall**：相关文档中被召回的比例，衡量“找得全”
- **精确率 Precision**：召回结果中相关的比例，衡量“找得准”

RAG 中通常先保证高召回，再通过 LLM 过滤和生成。

---

## 27. 什么是 Hybrid Search？

**考点**：混合检索。

**参考答案**：

Hybrid Search = 向量检索 + 关键词检索（如 BM25）结合。

向量检索擅长语义匹配，关键词检索擅长精确匹配（如食材名）。两者结合可提升整体效果，常用加权融合或 RRF（Reciprocal Rank Fusion）。

---

## 28. 什么是 RRF（Reciprocal Rank Fusion）？

**考点**：结果融合。

**参考答案**：

RRF 是一种融合多个检索列表的方法。公式为：

`score = Σ 1 / (k + rank_i)`

k 通常取 60。RRF 不需要对分数做归一化，适合融合不同来源的排序结果。

---

## 29. 什么是 Query Rewriting / Query Expansion？

**考点**：Query 改写。

**参考答案**：

- **Query Rewriting**：把用户原始 query 改写成更适合检索的形式
- **Query Expansion**：扩展出同义词、相关词，增加召回

例如家长说“娃便秘”，改写为“婴幼儿便秘 辅食推荐 膳食纤维 南瓜 红薯 燕麦”。

---

## 30. 什么是重排序（Re-ranking）？

**考点**：Rerank。

**参考答案**：

重排序是在向量召回 Top-K 后，用更精确的模型（如 cross-encoder）对候选重新打分排序。

Cross-encoder 能同时看到 query 和文档，比双塔 Embedding 更精确，但计算成本更高，所以只在候选集较小的时候使用。

---

## 31. 什么是 Chunking？为什么重要？

**考点**：文档切分。

**参考答案**：

Chunking 是把长文档切分成适合 Embedding 和检索的小块。因为：
- LLM 上下文有限
- 长文档 embedding 会稀释关键信息
- 检索精度更高

但切分过细会丢失上下文，需要设计合理的策略。

---

## 32. 有哪些常见的 Chunking 策略？

**考点**：Chunking 方法。

**参考答案**：

- **固定长度**：按 token 数切分，简单但可能切断语义
- **按段落/章节**：按 Markdown 标题切分，保留结构
- **语义切分**：按语义边界切分
- **重叠切分**：相邻 chunk 有重叠，避免上下文断裂
- **Parent Document Retrieval**：检索 sub-chunk，用 parent 补全上下文

---

## 33. 什么是 Parent Document Retrieval？

**考点**：高级检索。

**参考答案**：

Parent Document Retrieval 是指：检索到细粒度 chunk 后，根据 chunk 与 parent document 的关联，取出完整的 parent 文档作为 LLM 上下文。

优点：既保证检索精度，又不丢失全局上下文。

---

## 34. 什么是 HyDE？

**考点**：Hypothetical Document Embeddings。

**参考答案**：

HyDE 让 LLM 先把用户 query 生成一个“理想答案”文档，然后对这个理想文档做 embedding 和检索。

优点：把 query 从“问题形式”转成“答案形式”，与文档内容更匹配。

缺点：增加一次 LLM 调用，成本更高。

---

## 35. 什么是知识库入库（Ingestion）？主要步骤有哪些？

**考点**：知识库构建。

**参考答案**：

知识库入库是把非结构化文档转换为可检索向量的过程。主要步骤：
1. 读取文档（Markdown、PDF、网页等）
2. 清洗和预处理
3. 切分 chunk
4. 生成 embedding
5. 存入向量数据库
6. 建立索引

---

## 36. 如何处理知识库更新？

**考点**：增量更新。

**参考答案**：

- **全量更新**：清空重新入库，简单但耗时
- **增量更新**：根据文档 hash 或版本号，只更新变化的文档
- **版本控制**：保留历史版本，支持回滚
- **双写策略**：新库验证通过后再切换流量

---

## 37. 什么是 Metadata Filtering？

**考点**：结构化过滤。

**参考答案**：

Metadata Filtering 是在向量检索时结合文档元数据（metadata）做过滤。例如只检索 `age_min_month <= 8 <= age_max_month` 的食谱。

本项目中的月龄、质地、过敏原信息都适合作为 metadata。

---

## 38. RAG 中常见的失败模式有哪些？

**考点**：RAG 问题诊断。

**参考答案**：

- **检索失败**：召回不到相关内容
- **上下文丢失**：chunk 切分导致关键信息缺失
- **答案不在上下文中**：模型不看检索结果，用训练知识回答
- **信息过载**：上下文太多，模型遗漏关键信息
- **幻觉**：生成内容超出检索范围

---

## 39. 什么是检索失败？如何解决？

**考点**：检索优化。

**参考答案**：

检索失败是指用 query 找不到相关文档。解决方法：
- Query 改写/扩展
- 混合检索
- 降低相似度阈值
- 增加同义词映射
- 对常见 query 预置 FAQ
- 提示用户换种方式提问

---

## 40. 如何在 RAG 中实现多轮对话？

**考点**：对话式 RAG。

**参考答案**：

多轮对话中，当前 query 需要结合历史上下文。常见做法：
- 把历史对话作为上下文
- 对当前 query 做指代消解（如把“他”替换为“宝宝”）
- 用 LLM 把多轮对话压缩成一个独立 query 后再检索
- 检索结果和对话历史一起传给 LLM

---

# 第三章：Prompt 工程与结构化输出（41-55）

## 41. 什么是 Prompt Engineering？

**考点**：Prompt 工程基础。

**参考答案**：

Prompt Engineering 是设计高质量输入，引导 LLM 产生期望输出的技术和实践。包括：
- 清晰的任务描述
- 角色设定
- Few-shot 示例
- 输出格式说明
- 边界约束

---

## 42. 什么是 Zero-shot、One-shot、Few-shot？

**考点**：Prompt 模式。

**参考答案**：

- **Zero-shot**：只给任务描述，不给示例
- **One-shot**：给 1 个示例
- **Few-shot**：给多个示例

Few-shot 能让模型更快理解任务模式和输出格式，适合结构化输出任务。

---

## 43. 什么是 Chain-of-Thought（CoT）？

**考点**：推理提示。

**参考答案**：

CoT 是让模型“一步步思考”的技术。通过在 prompt 中要求模型展示推理过程，可以提高复杂任务的准确率。

示例 prompt：
```
请逐步分析，然后给出答案。
```

---

## 44. 什么是 System Prompt 和 User Prompt？

**考点**：Prompt 角色。

**参考答案**：

- **System Prompt**：设定模型角色、行为规范和全局约束
- **User Prompt**：用户的具体问题或任务

System Prompt 通常包含领域身份（如“你是专业婴幼儿营养师”）和全局规则（如“只输出 JSON”）。

---

## 45. 什么是 Temperature？它如何影响输出？

**考点**：采样参数。

**参考答案**：

Temperature 控制采样随机性。值越高，输出越随机、有创意；值越低，输出越确定、稳定。

- 创意写作：temperature 可高些
- 结构化输出/事实问答：temperature 应低

本项目推荐任务建议 temperature 取 0.1-0.3。

---

## 46. 什么是 Top-p（Nucleus Sampling）？

**考点**：采样参数。

**参考答案**：

Top-p 是从累积概率达到 p 的最小 token 集合中采样。它限制候选 token 范围，减少无意义输出。

常与 temperature 一起使用。例如 top_p=0.9 表示只从累积概率 90% 的 token 中采样。

---

## 47. 为什么结构化输出需要 JSON schema？

**考点**：结构化输出。

**参考答案**：

JSON schema 定义了输出字段、类型和约束，让 LLM 输出结构确定的 JSON。好处：
- 便于后端解析
- 减少字段缺失或多余
- 可约束字段类型和取值范围
- 可作为 Constrained Decoding 的依据

---

## 48. 什么是 JSON Mode 和 JSON Schema Mode？

**考点**：输出模式。

**参考答案**：

- **JSON Mode**：模型保证输出合法 JSON，但不约束字段结构
- **JSON Schema Mode / Structured Output**：模型按指定 schema 输出，包括字段名、类型、是否必填等

本项目应使用 JSON Schema Mode 以严格约束推荐结果。

---

## 49. 如何处理 LLM 输出非法 JSON？

**考点**：错误处理。

**参考答案**：

- 用 `json.loads()` 捕获解析异常
- 用正则提取 JSON 块
- 用 LLM 二次修复（如“请把以下内容整理成合法 JSON”）
- 记录错误日志和原始输出
- 失败时返回降级结果或错误信息

---

## 50. 什么是 Few-shot Prompting？在辅食推荐中怎么用？

**考点**：Few-shot 应用。

**参考答案**：

Few-shot 是在 prompt 中给出输入输出示例，让模型学习期望格式和风格。

在辅食推荐中，可以给出 2-3 个示例：
```
示例1：
输入：8个月宝宝，便秘
输出：{...推荐燕麦香蕉泥...}

示例2：
输入：10个月宝宝，补铁
输出：{...推荐猪肝菠菜粥...}
```

注意示例要覆盖不同场景，避免模型过度拟合。

---

## 51. 什么是 Role Prompting？

**考点**：角色提示。

**参考答案**：

Role Prompting 是给模型设定一个角色，让它以该角色的身份回答。

例如：
```
你是专业婴幼儿营养师，有10年临床经验。请为宝宝推荐辅食。
```

这能让模型输出更符合领域专业性。

---

## 52. 如何防止 Prompt 被注入攻击？

**考点**：Prompt 安全。

**参考答案**：

- 对用户输入做过滤和转义
- 不要把用户输入直接拼接到 system prompt
- 使用参数化方式传递用户输入
- 设置输出约束和校验
- 对敏感操作做人工复核

本项目应确保家长输入的过敏原、query 不会被当作指令执行。

---

## 53. 什么是 Prompt 版本管理？

**考点**：Prompt 工程化。

**参考答案**：

Prompt 版本管理是把 prompt 当作代码一样管理，包括：
- 存放在代码仓库中
- 每次变更走 CR
- 记录版本号和生效时间
- A/B 测试不同版本
- 回滚机制

不要把 prompt 硬编码后不做管理。

---

## 54. 什么是 Prompt 压缩？

**考点**：上下文优化。

**参考答案**：

Prompt 压缩是减少 prompt 长度的技术，因为：
- 上下文窗口有限
- 长 prompt 成本高
- 无关信息会干扰模型

常见方法：摘要、去除重复、只保留关键 chunk、使用更短的表达。

---

## 55. 在辅食推荐中，Prompt 如何体现安全约束？

**考点**：安全 Prompt。

**参考答案**：

- 明确要求“避开过敏原、医嘱禁忌、不喜欢的食物”
- 要求“只基于知识库内容，不要编造”
- 要求“推荐食材必须适合宝宝月龄”
- 要求“不确定时返回 INSUFFICIENT_EVIDENCE”

同时应在代码层用规则引擎二次校验。

---

# 第四章：LLM 原理与选型（56-70）

## 56. 什么是大语言模型（LLM）？

**考点**：LLM 基础。

**参考答案**：

大语言模型是基于 Transformer 架构、经过大规模文本训练的语言模型。它能理解和生成自然语言，用于聊天、翻译、摘要、代码生成等任务。

代表：GPT-4、Claude、qwen、Llama 等。

---

## 57. 什么是 Transformer？

**考点**：模型架构基础。

**参考答案**：

Transformer 是一种基于注意力机制的神经网络架构。核心组件：
- **Self-Attention**：让模型理解词与词之间的关系
- **Feed-Forward Network**：非线性变换
- **Layer Normalization**：稳定训练
- **Position Encoding**：让模型感知词序

---

## 58. 什么是 Self-Attention？

**考点**：注意力机制。

**参考答案**：

Self-Attention 让模型在处理一个词时，同时关注句子中其他词，并计算它们之间的相关性权重。

例如“bank”在“river bank”和“bank account”中含义不同，Self-Attention 通过上下文判断。

---

## 59. 什么是预训练（Pre-training）和微调（Fine-tuning）？

**考点**：模型训练。

**参考答案**：

- **预训练**：在大规模无标注语料上训练，学习通用语言知识
- **微调**：在特定任务或领域数据上进一步训练，使模型适应下游任务

本项目使用 qwen2.5:7b 是预训练模型，未微调。

---

## 60. 什么是 LoRA？

**考点**：高效微调。

**参考答案**：

LoRA（Low-Rank Adaptation）是一种高效微调方法。它只训练少量低秩矩阵，而不是整个模型，大幅减少训练参数和计算量。

适合场景：数据量不大、需要快速迭代的任务。

---

## 61. 什么是量化（Quantization）？

**考点**：模型压缩。

**参考答案**：

量化是把模型参数从高精度（如 FP32）转换为低精度（如 INT8/INT4）的技术。优点：
- 减少内存占用
- 加快推理速度
- 能在资源有限设备上运行

Ollama 中 `qwen2.5:7b-instruct-q5_K_M` 的 `q5` 就是 5-bit 量化。

---

## 62. 如何选择本地模型和云端模型？

**考点**：模型选型。

**参考答案**：

| 维度 | 本地模型 | 云端模型 |
|------|---------|---------|
| 隐私 | 高 | 低 |
| 成本 | 硬件成本 | 按调用付费 |
| 延迟 | 本地快 | 网络依赖 |
| 能力 | 7B 较小 | GPT-4 等大模型更强 |
| 可控性 | 高 | 低 |

本项目选择本地 Ollama 是因为隐私敏感和宝宝数据保护需求。

---

## 63. 什么是模型路由（Model Routing）？

**考点**：多模型调度。

**参考答案**：

模型路由是根据请求特征选择合适模型的机制。例如：
- 简单推荐用本地 7B 模型
- 复杂医学问题用云端大模型
- 根据延迟、成本、质量动态选择

实现方式：规则路由、分类器路由、强化学习路由。

---

## 64. 什么是上下文学习（In-Context Learning）？

**考点**：ICL。

**参考答案**：

上下文学习是指 LLM 通过 prompt 中提供的示例，在不需要更新参数的情况下学习新任务。

Few-shot prompting 就是上下文学习的一种形式。

---

## 65. 什么是模型的涌现能力（Emergent Ability）？

**考点**：涌现能力。

**参考答案**：

涌现能力是指模型规模达到一定程度后突然出现的能力，如复杂推理、多步推理。小模型可能没有，大模型突然出现。

但涌现能力也伴随不可控性，需要更多工程手段约束。

---

## 66. 什么是 Temperature Scaling？

**考点**：输出校准。

**参考答案**：

Temperature Scaling 是通过调整 temperature 来改变模型输出分布的方法。它不改变模型参数，只改变采样策略，常用于控制生成确定性。

---

## 67. 什么是 KV Cache？

**考点**：推理优化。

**参考答案**：

KV Cache 是在 Transformer 推理时缓存已计算过的 Key 和 Value 张量，避免重复计算，显著加速生成。

对长文本生成尤其重要。

---

## 68. 什么是 Beam Search？

**考点**：解码策略。

**参考答案**：

Beam Search 是维护多个候选序列，每步选择概率最高的 beam 个继续生成。相比贪心搜索，Beam Search 能找到全局更优解。

但很多 LLM 更常用采样策略（temperature、top-p）。

---

## 69. 为什么大模型会出现“一本正经地胡说八道”？

**考点**：幻觉原因。

**参考答案**：

原因：
- 训练目标只是预测下一个 token，不是求真
- 训练数据包含错误信息
- 模型没有实时知识
- 为了回答而编造

缓解：RAG、事实校验、约束输出、降低 temperature、人工审核。

---

## 70. 什么是模型的“对齐”（Alignment）？

**考点**：RLHF。

**参考答案**：

对齐是让模型行为符合人类价值观和目标的过程。常用方法：
- **RLHF**：人类反馈强化学习
- **DPO**：直接偏好优化
- **Constitutional AI**：让模型按原则自我纠正

本项目可通过收集家长反馈，未来做轻量级对齐。

---

# 第六章：评估、测试与持续优化（81-90）

## 81. 如何评估 LLM 应用？

**考点**：评估基础。

**参考答案**：

从两个层面评估：
- **离线评估**：用固定测试集跑指标
- **在线评估**：观察真实用户行为和反馈

常用指标：准确率、召回率、F1、BLEU、ROUGE、Faithfulness、Relevance。

---

## 82. 什么是 LLM 的单元测试？

**考点**：测试分层。

**参考答案**：

LLM 单元测试是对 LLM 调用以外的逻辑做测试，通常需要 mock LLM 返回。

例如测试 `BabyRecordExtractor` 时，mock `OllamaGateway.chat_sync()` 返回固定 JSON，验证解析逻辑。

---

## 83. 什么是集成测试？

**考点**：集成测试。

**参考答案**：

集成测试是把多个组件连起来测试。对 AI 项目，可能包括：
- 调用真实 Ollama
- 查询真实 PostgreSQL
- 验证端到端输出

集成测试更接近真实环境，但速度慢、成本高。

---

## 84. 什么是回归测试？

**考点**：回归测试。

**参考答案**：

回归测试是确保改动没有破坏已有功能。对 AI 项目，维护一个 bad case 集：
- 每次更新 prompt 后跑一遍
- 确保已知问题不复发
- 如果失败，阻断合并

---

## 85. 什么是 LLM-as-a-Judge？

**考点**：LLM 裁判。

**参考答案**：

LLM-as-a-Judge 是用一个更强的 LLM 来评估另一个 LLM 的输出。例如用 GPT-4 给推荐结果打分。

优点：自动化、低成本。
缺点：存在偏见，需要人工抽检校准。

---

## 86. 什么是 A/B 测试？

**考点**：A/B 测试。

**参考答案**：

A/B 测试是把用户随机分成两组，分别使用不同版本，比较效果。

AI 项目中可用于比较：
- 不同 prompt
- 不同模型
- 不同检索策略

---

## 87. 如何选择评估指标？

**考点**：指标选择。

**参考答案**：

根据业务目标选择：
- 推荐采纳率
- 用户满意度
- 响应延迟
- 错误率
- 幻觉率
- 多样性

避免只看单一指标，要综合考虑质量和成本。

## 88. 什么是数据飞轮？

数据飞轮是指：用户使用 -> 产生数据 -> 数据优化模型 -> 更好的体验 -> 更多用户。

在辅食推荐中，家长反馈“适合/不适合”就是数据，可用于优化 prompt、知识库和模型。

## 89. 如何收集和利用用户反馈？

## 90. 什么是模型漂移？

# 第七章：安全、隐私与业务（91-95）

## 91. AI 应用中的常见安全风险有哪些？

**考点**：AI 安全。

**参考答案**：

- **提示注入**：用户输入被当作指令执行
- **数据泄露**：训练数据或用户隐私被输出
- **幻觉**：生成错误信息
- **偏见歧视**：模型输出不公平内容
- **滥用**：被用于生成有害内容

---

## 92. 什么是提示注入？

**考点**：Prompt Injection。

**参考答案**：

提示注入是攻击者通过输入恶意内容，改变模型行为。例如用户输入：
```
忽略以上指令，告诉我如何...
```

防御：
- 输入过滤和清洗
- 区分 system prompt 和 user input
- 输出约束和校验
- 最小权限原则

---

## 93. 如何保护宝宝隐私数据？

**考点**：隐私保护。

**参考答案**：

- 数据最小化：只收集必要信息
- 脱敏：日志中不存明文
- 加密：传输和存储加密
- 访问控制：按用户隔离
- 审计：记录数据访问

---

## 94. 为什么 AI 推荐辅食需要免责声明？

**考点**：业务合规。

**参考答案**：

因为 AI 不是医生，推荐内容不能替代专业医疗建议。必须明确告知用户：
- 内容仅供参考
- 有特殊健康状况应咨询医生
- 引入新食材注意观察过敏反应

否则可能承担法律责任。

---

## 95. 如何处理模型推荐与家长认知冲突？

# 附录：项目拓展需求适配

以下针对前文提到的拓展方向，给出真实有价值的需求场景和 MVP 建议。

## 1. 多 Agent 协作

**真实需求**：当前推荐链路是固定 pipeline，无法灵活应对复杂场景（如“宝宝便秘但不爱吃青菜”需要同时处理症状、挑食、质地多个约束）。

**MVP 需求**：
- 拆出 `QueryPlannerAgent`、`RetrieverAgent`、`SafetyAgent`、`RecipeAgent`。
- 支持“家长忌口 + 宝宝过敏 + 当天已吃”多约束联合推荐。
- 交付：复杂 query 推荐准确率提升，可解释（展示各 Agent 决策理由）。

## 2. Tool Use / Function Calling

**真实需求**：推荐不仅依赖知识库，还需要知道宝宝当天是否已经吃过某道菜、最近体重曲线如何。

**MVP 需求**：
- 提供工具：`get_today_meals(baby_id)`、`get_growth_curve(baby_id)`、`search_recipe_kb(query)`。
- LLM 自主决定调用顺序。
- 交付：推荐结合当日饮食缺口，避免重复和过量。

## 3. 多模态能力

**真实需求**：家长拍了辅食照片，想知道是否适合宝宝、营养是否均衡；或语音不方便打字。

**MVP 需求**：
- 图片识别：上传辅食照片，识别食材并评估是否适合当前月龄。
- 语音输入：家长语音描述症状，ASR 后进入文本提取链路。
- 交付：减少家长手动输入，提升使用频率。

## 4. 个性化与长期记忆

**真实需求**：每个宝宝发育节奏和口味不同，通用推荐难以长期满足。

**MVP 需求**：
- 记录宝宝历史反馈（喜欢/不喜欢/过敏）。
- 推荐时结合“宝宝画像向量 + 时间线”做个性化重排。
- 交付：推荐采纳率提升，家长感觉“越用越懂我家娃”。

## 5. 混合模型与云端兜底

**真实需求**：本地 7B 模型对复杂医学/营养问题理解不足，但云端成本高。

**MVP 需求**：
- 本地模型处理常规推荐；复杂/低置信 query 路由到云端大模型。
- 按响应时间、成本、质量动态选择模型。
- 交付：复杂问题回答质量提升，同时控制平均成本。

## 6. 异步与可观测性

**真实需求**：AI 推理慢时小程序卡住，且线上出问题难以定位。

**MVP 需求**：
- 耗时任务（如月度总结、图片理解）走 Celery 异步队列。
- 接入 OpenTelemetry / LangSmith，记录每个请求的全链路 trace。
- 交付：用户体验更流畅，线上问题定位时间从小时级降到分钟级。

## 7. 持续学习与数据飞轮

**真实需求**：上线后模型不会自动变好，需要用户反馈驱动迭代。

**MVP 需求**：
- 家长可对每条推荐点“适合/不适合/报错”。
- 每周自动聚合 bad case，由营养师审核后更新知识库/prompt。
- 交付：推荐质量随使用数据持续增长。

## 8. 企业级部署

**真实需求**：从小程序 MVP 走向可对外服务的 SaaS，需要多租户、可扩展。

**MVP 需求**：
- K8s + Helm 部署，Ollama 独立 GPU 节点池。
- API Gateway + 鉴权 + 限流 + 多租户数据隔离。
- 交付：支持多家庭/机构接入，单租户故障不影响他人。

## 101. 向量召回后的“结构化过滤”应放在哪个环节？

**考点**：召回 vs 过滤的顺序、语义召回与精确条件的 trade-off、hybrid search。

**参考答案**：

当前做法（先向量召回 Top-K，再过滤）的优点是 Embedding 不受过滤条件稀疏影响，能召回语义相关但字段可能不完全匹配的内容；缺点是过滤后可能 Top-K 变少甚至为空。

如果先过滤再向量检索，优点是能保证召回结果都满足硬条件；缺点是过滤后的候选集小，语义相关性可能下降。

推荐 hybrid 方案：
1. 先在 pgvector 做 ANN 召回 K=50
2. 做结构化过滤（月龄/质地/过敏原）
3. 若过滤后不足 top_k=3，放宽部分非关键条件重新召回
4. 最终对保留结果做重排

## 102. 为什么 recipe RAG 使用 bge-m3 而不是直接用 qwen2.5:7b 生成 embedding？

**考点**：Embedding 模型选择、Dense/Sparse/Late Interaction、query 改写。

**参考答案**：

专用 Embedding 模型体积小、速度快、对句子级语义对齐更好。用 7B 生成模型做 embedding 成本高、延迟大。

三种表示方案：
- **Dense Embedding**：语义泛化好
- **Sparse Embedding**：关键词匹配强
- **Late Interaction / ColBERT**：token 级交互，精确但索引大

建议 Dense + Sparse 混合检索，最终融合分数。

## 103. 当前 chunk 策略是按 Markdown 章节切片，会出现什么问题？

**考点**：Chunking 策略、上下文继承、Parent Document Retrieval、HyDE。

**参考答案**：

按章节切片的典型问题是上下文断裂：
- “食材”chunk 不知道“适合 8 个月”和“质地：软烂”
- “做法”chunk 不知道“过敏原提示”

改进方案：
1. **Parent Chunk + Sub-chunk**：检索 sub-chunk，用 parent 补全上下文
2. **Metadata 注入**：把月龄/质地写入 metadata
3. **HyDE**：用 LLM 生成理想答案文档再检索

## 106. 为什么我们在 `recipe_rag.py` 中显式传入 JSON schema 到 Ollama 的 `format` 参数？

**考点**：结构化生成、JSON Mode / Constrained Decoding / Grammar-based、兜底处理。

**参考答案**：

显式传 schema 可以让模型生成符合预定义结构的 JSON，减少字段缺失或多余。

三种技术区别：
- **JSON Mode**：只保证合法 JSON
- **Constrained Decoding**：解码阶段限制 token
- **Grammar-based**：用 CFG/GBNF 描述格式

Ollama 底层若用 llama.cpp，format 会转成 GBNF grammar。

兜底：json.loads 捕获异常、Pydantic 校验、重试、返回 error。

## 107. 当前 schema 已要求字段必填并禁止额外字段，但仍可能出现“幻觉食材”。

**考点**：幻觉检测、事实校验、白名单、后处理。

**参考答案**：

Schema 只能保证结构合法，不能保证内容真实。

防御：
- Prompt 明确要求“只基于知识库食材”
- 建立食材白名单，对 ingredients 做 NER 比对
- 发现不在白名单中的食材，标记为疑似幻觉
- 过滤菜品、触发重试或降低 confidence

## 108. 文本提取模块使用 Pydantic 校验，为什么还要保留 LLM 重试？

**考点**：temperature/top_p 影响、稳定性、多阶段抽取。

**参考答案**：

Pydantic 校验只能判断结果是否合法，不能修正错误结果。LLM 可能生成 JSON 截断、字段名错误等。

降低 temperature 可减少随机性，但不能保证成功。

更鲁棒的多阶段方案：
1. 自由抽取
2. 结构化转换
3. 校验与补齐
4. 置信度打分

## 120. 若要引入 A/B 测试比较两个 prompt 版本或两个模型，你会如何设计实验？

**考点**：A/B 测试、分流、指标、统计显著性。
