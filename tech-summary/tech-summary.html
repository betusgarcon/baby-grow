2.3 关键 Tailwind 类详解

Tailwind 类 对应 CSS 布局作用
flex flex-col display: flex; flex-direction: column 建立垂直弹性容器，子元素沿纵向排列
items-center align-items: center 水平居中对齐交叉轴元素
justify-between justify-content: space-between 主轴两端对齐，常用于导航栏左右分布
gap-2 gap: 0.5rem (8px) 设置 Flex 子元素之间的间距
px-4 padding-left: 1rem; padding-right: 1rem 水平方向内边距，创建内容与边缘的呼吸空间
min-h-screen min-height: 100vh 页面最小高度等于视口高度
flex-1 flex: 1 1 0% 填充剩余空间，用于 ScrollView 撑满
shrink-0 flex-shrink: 0 禁止 Flex 收缩，保持元素原始尺寸
pb-28 padding-bottom: 7rem (112px) 为底部 TabBar 预留空间，防止内容被遮挡
h-0 height: 0 ScrollView 配合 flex-1 实现正确的滚动区域
rounded-5xl border-radius: 2rem (32px) 大圆角卡片，符合设计稿的柔和风格
overflow-hidden overflow: hidden 裁剪溢出内容，防止布局异常

2.5 min-h-screen 与 flex-1 的协作

🎯 为什么需要两个类同时使用？

w-screen h-screen flex flex-col - 根容器占满整个视口，建立 Flex 列布局

flex-1 h-0 - ScrollView 必须使用 h-0 配合 flex-1，否则在小程序中会导致滚动区域计算错误。这是 Taro + 小程序的经典陷阱。

shrink-0 - Header 和 Footer 不能被 Flex 压缩，保持固有高度

💡 Props Down / Event Up 是什么？

Props Down（单向数据流）：父组件将数据通过 props 向下传递给子组件。子组件只能读取 props，不能直接修改。

Event Up（事件上抛）：子组件通过调用父组件传入的回调函数（如 onChange），将用户操作通知父组件。父组件决定如何处理这个变化。

为什么这样设计？：保持数据流的清晰可预测性。任何状态变化都有明确的"源头"，降低调试难度。

// 父组件：GrowthPage 中的状态管理

  // ← 回调函数下传
/>

4.4 为什么禁止使用原生类名

⚠️ 禁止使用的类名

禁止： bg-stone-50、text-slate-600、bg-neutral-100

替换为： 语义化 Token bg-surface、text-analysis-text-primary

🚫 为什么禁用 stone- / slate- / neutral-？

视觉不可控：原生类名是冷色系（stone/slate 偏灰蓝冷调），与项目暖色调设计语言冲突。设计稿使用温暖的米白、棕灰、森林绿。

可维护性差：如果将来调整配色方案，语义化 Token 只需改配置文件一处；原生类名需要全局搜索替换，容易遗漏。

设计系统割裂：混合使用两套命名体系（设计 Token + Tailwind 默认色），会让团队成员困惑，增加新成员上手成本。

强制使用方式：组件中的 style 对象会统一引用 analysisColors，Tailwind 类只用于布局和间距。

5.2 AnalysisChart 核心原理

📊 纯视图渲染是什么？

AnalysisChart 不依赖任何第三方图表库（虽然项目安装了 echarts），而是使用纯 CSS 技术绘制图表：

  • 折线图：用 absolute 定位每个数据点，用 transform: rotate() 旋转线段实现折线连接
  • 饼图/环图：使用 conic-gradient CSS 属性实现环形色块分布
  • 柱状图：用普通 View 组件，通过百分比设置高度
  • 堆叠条图：多段横向拼接的 View 组合

为什么不用 echarts？：小程序环境中第三方 canvas 图表嵌入 ScrollView 后容易出现漂移、层级错乱。纯视图方案更稳定，且不需要额外的 canvas 上下文。

// AnalysisChart 核心渲染逻辑
// 折线图：用旋转的 View 模拟折线
function renderLineChart(option) {
  const normalizedSeries = seriesList.map(series => ({
    ...series,
    points: series.points.map((point, index) => ({
      ...point,
      // 将数据映射为百分比坐标
      xPercent: monthToPercent(monthNumbers[index]),
      yPercent: 100 - ((point.value - minValue) / span) * 100,
    })),
  }))
  
  return normalizedSeries.map(series =>
    series.points.slice(0, -1).map((point, index) => {
      const nextPoint = series.points[index + 1]
      const dx = nextPoint.xPercent - point.xPercent
      const dy = nextPoint.yPercent - point.yPercent
      const width = Math.sqrt(dx * dx + dy * dy)
      const angle = (Math.atan2(dy, dx) * 180) / Math.PI
      
      return (
        // ← 关键：通过旋转 View 实现折线
          style={{
            transform: `rotate(${angle}deg)`,
            width: `${width}%`,
          }}
        />
      )
    })
  )
}

7.2 决策详情

选择 使用 Flexbox 而非 Grid 布局
为什么选择

移动端页面是一维滚动布局（垂直为主），Flex 的主轴对齐更自然。Grid 在二维布局上更有优势，但当前项目只有卡片网格（如情绪日历）需要二维布局，使用 grid-cols-7 等简单 Grid 即可，主布局用 Flex 更合适。

代价

复杂对齐场景（如不规则瀑布流）需要额外的 CSS hack。Flex 在某些极端对齐场景下不如 Grid 灵活，但当前项目未遇到此问题。

选择 组件局部 useState 而非全局状态管理
为什么选择

项目中大部分状态是页面级别的（如当前选中的指标、时间范围、筛选条件），不需要跨页面共享。Zustand、Redux 等全局状态库会增加复杂度，而 useReducer 或 useState 足够应对当前需求。只有当需要跨页面持久化（如用户设置、登录态）时，才需要引入全局状态。

代价

如果未来需要跨页面共享状态（如从列表页跳转到详情页保持筛选条件），需要额外实现状态传递机制（如 URL 参数、全局 Context）。

选择 Props Down / Event Up 单向数据流
为什么选择

单向数据流让数据流向清晰可追溯。父组件持有状态，子组件只通过 props 接收数据和回调，避免了双向绑定的复杂性。每个组件都是独立单元，易于测试和复用。配合 TypeScript 类型系统，可以在编译期捕获 props 传递错误。

代价

对于深层嵌套组件，需要逐层传递 props（props drilling）。当前项目最多3层嵌套，不构成问题。如果将来出现深层嵌套，可以考虑引入 Context 或状态提升模式。

选择 Tailwind 语义化 Token 而非原生类名
为什么选择

设计系统需要统一的视觉语言。bg-surface vs bg-stone-50，前者是"设计语义"，后者是"技术实现"。当设计师说"卡片用浅背景"，你不会知道要用 stone-50 还是 slate-100，但你知道要用 analysis-card-muted-bg。

代价

需要在 tailwind.config.js 中维护一份 Token 映射，以及在 analysisTokens.ts 中维护一份运行时副本。两处可能不一致，需要建立维护流程。

选择 纯视图渲染图表而非 echarts canvas
为什么选择

小程序环境中，canvas 图表嵌入 ScrollView 后存在多个已知问题：1) 层级计算异常，canvas 组件总是置顶；2) 滚动时渲染不同步；3) 动画卡顿。纯视图方案（View + CSS Transform）规避了这些问题，且渲染性能在简单图表场景下足够好。

代价

无法实现复杂交互（如拖拽缩放、tooltip 跟随鼠标）。如果未来需要高级图表功能，需要重新评估 echarts-weapp 或其他方案。当前业务场景（静态趋势展示、占比统计）不需要这些功能。

选择 Taro + React 而非原生小程序
为什么选择

团队已有 React 经验。Taro 允许使用 React 语法和组件化思维开发小程序，降低学习成本。同时支持多端输出（微信/H5/支付宝），如果未来需要 Web 版或其他平台，代码可以复用。TypeScript 类型系统在大型项目中提供可靠的重构支持。

代价

Taro 存在版本兼容问题（如 weapp-tailwindcss 版本匹配），部分小程序原生 API 需要通过 Taro 封装调用，调试时需要理解 Taro 和小程序两层编译产物。

选择 集中 Mock 数据 + TypeScript 类型定义
为什么选择

所有页面共用同一份 Mock 数据，确保数据一致性。TypeScript 接口定义在 Mock 文件顶部，既是数据类型的单一来源，也是 API 对接时的契约。迁移到真实 API 时，只需替换数据的来源方式，所有下游组件和类型定义都不需要修改。

代价

当前 Mock 数据是硬编码的，如果不同页面需要不同的模拟数据场景，需要在 Mock 文件中维护多份数据或创建工厂函数。

选择 CSS flex-1 h-0 实现 ScrollView 高度
为什么选择

小程序 ScrollView 组件需要明确的高度才能正确计算滚动范围。使用 flex-1 h-0 组合，flex-1 让 ScrollView 填充剩余空间，h-0 强制它从 0 开始计算高度（而不是由内容撑开），确保滚动行为正确。这是 Taro + 小程序的经典"陷阱"，不遵循会导致：1) ScrollView 无限高无法滚动；2) 内容超出屏幕不显示滚动条。

代价

新开发者需要理解 flex-1 h-0 的配合原理，这不是直觉性的行为。建议在项目文档中明确记录此模式。

📚 总结与建议

这份文档涵盖了 Baby Growth 项目的核心技术架构。作为后续开发者，建议：

  1. 理解布局模式：所有页面遵循相同的三段式 Flex 布局，掌握 flex-1 h-0 和 pb-28 的协作
  2. 使用 Token 而非原生类名：新增颜色务必在 tailwind.config.js 中定义语义化 Token
  3. 保持 Props Down 模式：新增组件不要引入全局状态，保持单向数据流
  4. 图表优先用 AnalysisChart：当前方案足够支撑业务需求，避免过早引入 echarts
  5. Mock → API 迁移：在 API 层封装数据，保持组件接口不变

本报告基于项目源码分析生成，所有代码示例均来自真实文件。希望能帮助你更好地理解和维护这个项目。
